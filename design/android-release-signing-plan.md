# Release signing, and why the keystore is yours to generate

Vince · brief · written August 3, 2026

## 1. Trigger

`crane-plan.md`'s Android gaps checklist has carried this since Bittern:
"without it the APK cannot be given to anyone but the person who built it."
`app/build.gradle.kts`'s `release` build type has never had a signing
config, so `assembleRelease` has always produced `app-release-unsigned.apk`
— buildable, not installable anywhere but a machine willing to trust an
unsigned APK.

## 2. Why this session generates the wiring but not the key

An earlier attempt in this same worktree tried to generate the keystore and
write its password to `local.properties` directly. The session's own
classifier denied the write — correctly: a freshly generated, opaque
password persisted to disk with no human ever seeing it is exactly the
shape of action that guard exists to catch, regardless of the gitignored
destination being perfectly reasonable.

That is also, independently, the right way to do this. A release signing
key is not a rotatable credential — Android refuses to install an update
over an existing app if the signing key changes, so losing it means never
updating that installation again under its own identity. A key with that
much permanence is better generated by hand, once, by the person who will
be responsible for keeping it, than handed to an agent to generate and
momentarily hold even in passing.

## 3. What this slice did

`app/build.gradle.kts` reads four properties from `local.properties` —
`RELEASE_STORE_FILE`, `RELEASE_STORE_PASSWORD`, `RELEASE_KEY_ALIAS`,
`RELEASE_KEY_PASSWORD` — and only creates a `release` signing config if all
four are present. Nothing else changes: `assembleDebug` never reads these,
and `assembleRelease` with none of them set still builds successfully, still
unsigned, exactly as it always has. Verified both ways.

`local.properties` is already gitignored (it already holds `sdk.dir`,
machine-specific and never committed) — this is one more machine-specific
secret in the same file, not a new pattern.

## 4. What you do, once

Generate the keystore with `keytool` (ships with the JDK; Android Studio's
own JBR has one):

```powershell
& "$env:ProgramFiles\Android\Android Studio\jbr\bin\keytool.exe" -genkeypair -v `
  -keystore "$env:USERPROFILE\clarice-release.keystore.jks" `
  -alias clarice-release `
  -keyalg RSA -keysize 2048 -validity 10000 `
  -dname "CN=Clarice, OU=Development, O=Clarice, L=Unknown, ST=Unknown, C=US"
```

`keytool` prompts for a password interactively rather than taking one on
the command line — type one you'll keep. Modern `keytool` defaults to a
PKCS12 keystore, which requires the store password and the key password to
be the same; it will tell you so if you try to set them differently, so
just answer the same thing both times it asks.

The keystore path above is outside the repository entirely
(`%USERPROFILE%`), which is one reasonable place — anywhere you'll reliably
back it up works, including inside `android/` itself (`*.jks` is already
gitignored there). **Back it up somewhere durable.** There is no recovery
if it's lost — only a new key, a new signing identity, and every existing
install unable to receive it as an update.

Then add four lines to `android/local.properties` (create the file if it
doesn't exist yet — it's the same file Android Studio writes `sdk.dir`
into):

```properties
RELEASE_STORE_FILE=C\:\\Users\\vince\\clarice-release.keystore.jks
RELEASE_STORE_PASSWORD=<the password you chose>
RELEASE_KEY_ALIAS=clarice-release
RELEASE_KEY_PASSWORD=<the same password you chose>
```

Windows paths in a `.properties` file need `\\` for each backslash and `\:`
for the drive colon, per Java's `Properties` format — the example above is
escaped correctly for the path `keytool` was given.

Once that file has all four lines, `:app:assembleRelease` produces a signed
`app-release.apk` instead of `app-release-unsigned.apk`. Nothing else
changes; `:app:assembleDebug` and the whole test suite are unaffected
either way.

## 5. Verification

This session: `assembleDebug`, `assembleRelease` and `testDebugUnitTest`
all still pass with `local.properties` unset. Confirmed the release
artifact is still named `app-release-unsigned.apk`, i.e. genuinely
unsigned, not silently signed with something unexpected.

Once you've generated the keystore and added the properties: `./gradlew.bat
:app:assembleRelease` should produce `app-release.apk`, and `apksigner
verify app-release.apk` (in `$ANDROID_HOME/build-tools/<version>/`) confirms
it. That verification step is yours to run — it's the first moment the key
actually exists.
