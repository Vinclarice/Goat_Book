# Release signing, and why the keystore is yours to generate

Vince · brief · written August 3, 2026 · **build wired, key not generated**

## 1. State

`app/build.gradle.kts` reads `RELEASE_STORE_FILE`, `RELEASE_STORE_PASSWORD`,
`RELEASE_KEY_ALIAS` and `RELEASE_KEY_PASSWORD` from `local.properties` and
creates a `release` signing config only if all four are present. Its own
comment states the rest: `assembleDebug` never reads them, and
`assembleRelease` with none of them set still builds, unsigned, as it always
has. Verified both ways, alongside `testDebugUnitTest`, and the release
artifact confirmed still named `app-release-unsigned.apk` — genuinely
unsigned, not silently signed with something unexpected.

`local.properties` is already gitignored and already holds `sdk.dir`, so this
is one more machine-specific secret in the same file, not a new pattern.

Until the keystore below exists, `assembleRelease` produces
`app-release-unsigned.apk`, which is buildable but installable nowhere except a
machine willing to trust an unsigned APK — the gap `crane-plan.md`'s Android
checklist has carried since Bittern.

## 2. Why the key is yours and not an agent's

A release signing key is not a rotatable credential. Android refuses to install
an update over an existing app if the signing key changes, so losing it means
never updating that installation again under its own identity. A key with that
much permanence is better generated by hand, once, by the person responsible
for keeping it, than handed to an agent to generate and momentarily hold.

## 3. What you do, once

Generate the keystore with `keytool`, which ships with the JDK — Android
Studio's own JBR has one:

```powershell
& "$env:ProgramFiles\Android\Android Studio\jbr\bin\keytool.exe" -genkeypair -v `
  -keystore "$env:USERPROFILE\clarice-release.keystore.jks" `
  -alias clarice-release `
  -keyalg RSA -keysize 2048 -validity 10000 `
  -dname "CN=Clarice, OU=Development, O=Clarice, L=Unknown, ST=Unknown, C=US"
```

`keytool` prompts for the password interactively rather than taking it on the
command line — type one you'll keep. Modern `keytool` defaults to a PKCS12
keystore, which requires the store password and the key password to be the
same, so answer identically both times it asks.

`%USERPROFILE%` puts the keystore outside the repository, which is one
reasonable place; anywhere you'll reliably back it up works, including inside
`android/` itself, where `*.jks` is already gitignored. **Back it up somewhere
durable.** There is no recovery if it is lost — only a new key, a new signing
identity, and every existing install unable to receive an update.

Then add four lines to `android/local.properties`, creating the file if
Android Studio has not already written `sdk.dir` into it:

```properties
RELEASE_STORE_FILE=C\:\\Users\\vince\\clarice-release.keystore.jks
RELEASE_STORE_PASSWORD=<the password you chose>
RELEASE_KEY_ALIAS=clarice-release
RELEASE_KEY_PASSWORD=<the same password you chose>
```

Windows paths in a `.properties` file need `\\` for each backslash and `\:` for
the drive colon, per Java's `Properties` format; the example is escaped
correctly for the path `keytool` was given.

## 4. Verifying it worked

`.\gradlew.bat :app:assembleRelease` should then produce `app-release.apk`
rather than `app-release-unsigned.apk`, and `apksigner verify app-release.apk`
(in `$ANDROID_HOME/build-tools/<version>/`) confirms it. That step is yours to
run — it is the first moment the key actually exists. Nothing else changes:
`assembleDebug` and the test suite are unaffected either way.
